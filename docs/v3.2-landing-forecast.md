# v3.2 plan: landing-page grouping + full-year forecast

Status: **implemented + verified 2026-10-19** (migration + engine + seeds;
verified live on thor.local; see §Verification).

v3.2 is a **report-hub** release with two independent changes:

1. **Landing-page grouping.** The index page was a flat list of every
   active dashboard. It now renders grouped sections (one heading per
   group): **Finance — expense analysis** (all the money dashboards,
   including the finance-ingestion data-health dashboard), **Data Hub**
   (the cross-dataset registry), and **Demo / test data** (the hub demo).
   Grouping is DB-driven (`dashboards.section` + `sort_order`), so the AI
   can re-group or add a new section without a rebuild.
2. **Full-year forecast on `/d/yearly`.** For the current (partial) year,
   the spend KPI is year-to-date, so a naive YoY delta understates the
   year. v3.2 adds a **linear-trend forecast** of full-year spend and
   compares the *forecast* (not the YTD figure) to the prior year, so the
   YoY delta always compares full years. A note card makes the basis
   explicit.

One small migration (two columns on `dashboards`), a few engine changes
(index grouping), seed updates (section/sort_order on all 9 dashboards +
the forecast query/cards on `yearly`), no data-hub changes, no
`finance`/`hub` schema changes.

## 1. Goals

1. **Group the landing page.** All finance/expense dashboards under one
   heading (including the finance-ingestion data-health dashboard); the
   hub demo in its own section; the cross-dataset Data Hub on its own.
2. **Compare full years on `/d/yearly`.** When the selected year is the
   current (partial) year:
   - clearly indicate it is not a full year;
   - show the spend-to-date;
   - forecast full-year spend with a simple linear trend;
   - use the **forecast** (not the YTD figure) for the +/- % vs the prior
     year.

## 3. Design notes

- **Linear trend = OLS on monthly spend.** For the selected year, build a
  Jan–Dec spine of monthly spend (cents; spend = negative amounts
  excluding Transfer/Income, same convention as every other card). Fit a
  line to the months that have data (month 1..N where N = the last month
  with spend > 0) and extrapolate to 12 months:
  `forecast = Σ_{m=1..12} (a + b·m)` where `b = (N·Σxy − Σx·Σy) /
  (N·Σx² − (Σx)²)` and `a = (Σy − b·Σx) / N`. Degenerate cases: no data →
  0; one month → `spend × 12`.
- **Full years are actuals.** When `:year < current year`, the "forecast"
  is just the actual full-year spend (the CASE short-circuits to the sum),
  so the forecast card and the YoY delta are identical to the pre-v3.2
  behavior for past years. Only the current (partial) year uses the
  trend line.
- **The delta compares full years.** The "Spend in :year" card's delta is
  `forecast / prior_year_actual − 1`. For the current year that is
  `forecast(current) / actual(prior) − 1`; for a past year it is
  `actual(year) / actual(prior) − 1`. The YTD figure is still shown as the
  card value (the honest "so far" number); the *comparison* is on a
  full-year basis.
- **Read-only contract preserved.** All of this is reads + stored content;
  the UI performs no writes. Grouping and the forecast are DB content
  (seeds) + read-time engine logic.
- **Escaping gotcha (seed authoring).** Card `config` is a **JSON**
  column, so a newline inside a config string must be written `\\n`
  (double-backslash) in the seed — the SQL string literal collapses it to
  the literal two-char `\n`, which is a valid JSON escape. A single `\n`
  becomes a real newline and the JSON column rejects it
  (`Invalid encoding in string`). Query `sql_text` is a **TEXT** column, so
  it takes a single `\n` (a real newline in the stored SQL). The v3.2
  forecast cards use `\\n` in their `config`; the forecast query's
  `sql_text` uses `\n`.
